# 后台权限刷新保留未保存操作

同一账号的 Supabase 登录状态通知会重新加载权限。原后台把每次 `accessLoading` 都当成首次加载，返回整页 spinner，导致题库发布窗口、选择和未保存表单被卸载。

只调整 `Admin.tsx` 的加载条件：已有管理员权限时，后台权限刷新保留当前组件；首次校验、切换到其他账号和无权限状态仍阻止后台挂载。权限请求返回拒绝或错误后，继续按现有逻辑隐藏后台；所有写入 RPC 的服务端鉴权不变。

## 回归证据

使用真实 Admin 组件和本地合成权限状态，不连接生产，不创建账号或题目。浏览器操作通过 CUA 完成。

| 场景 | 结果 |
| --- | --- |
| 修复前：新建题表单输入后进入同账号刷新状态 | 表单消失，成功复现 |
| 修复后：同账号刷新中 | 弹窗仍在，未保存题干完整保留 |
| 修复后：刷新完成 | 未保存题干完整保留 |
| 切换账号且新权限尚未返回 | 后台及弹窗隐藏 |
| 权限拒绝 | 跳转拒绝页面，后台隐藏 |
| 权限恢复 | 后台恢复可访问 |
| 退出登录 | 跳转登录页面，后台隐藏 |

- `npm run test:admin-access`：11/11。
- `npx tsc --noEmit -p tsconfig.app.json`、`npm run build`：通过。
- 新测试 fixture 的 ESLint：通过。Admin 原有 14 个 lint 错误及 1 个 warning 与修复前逐条一致，本次未新增；没有扩展本次范围清理旧问题。

## 复现

运行 `node scripts/admin-access/serve-auth-refresh-fixture.mjs`，打开 `http://127.0.0.1:5197/__auth-refresh-test`。添加 `O2I_AUTH_REFRESH_BASELINE=1` 则在 5198 端口运行修复前对照。

在 Question Bank → New question 输入题干，用页面列出的 Alt 快捷键切换合成权限状态。服务仅监听本机，测试 mock 不进入生产入口。上述本地结果不代替部署后的真实管理员发布验收。
