# 课程编号冲突与旧 Arena 迁移登记修复

## 原因与本次只读结论

2026-11-05 对已链接的生产项目 `lxoaeaewcrshjkigzyqe` 使用 Supabase Management API（`read_only: true`）重新核对。以下结论来自本次查询，不沿用旧记录作为当前部署证明。

1. `20261103020000` 已属于 `admin_user_deletion`；账本源文件 MD5 为 `d11ccb83ad64a84db35645599c39f9eb`，与仓库一致。课程登录限制误用了同一编号。生产的 `course_topic_visible`、`course_lesson_visible`、`get_course_outline_entry` 均与安装登录限制前的已知正文一致，尚未安装 Unit 4 登录限制。修复将未部署的课程文件原样改号为 `20261105010000_course_login_access.sql`，保留管理员迁移及其账本。
2. 旧 Arena 两表及三个 RPC 已存在，`arena_game` 账本缺失。将原始 Arena 迁移在禁网的一次性 PostgreSQL 17 容器实际执行后，生产目录与本地基线逐项相等：列、默认值、非空、主键/检查约束/外键、索引及有效性、所有者、表和列授权、RLS、策略、非系统触发器、函数定义及执行授权、匿名/普通账号的有效表权限。函数只规范化 CRLF 和行尾水平空格。可证明当前安装状态等价于原迁移，无法据此追溯是谁、通过哪条流程安装；不猜测安装历史。
3. 已另外检查课程表、视频映射、视频表和游戏存储的 RLS 及五条读取策略，均经过可见性函数。新修复不修改这些策略。

这是迁移身份冲突和安装登记遗漏；本次核对没有发现数据损坏证据，也不构成全库数据完整性审计。

## 计划与变更边界

- 给未部署的课程限制分配唯一的新编号，同步数据库测试引用；不改变功能内容。
- 旧 Arena 原迁移内容不变。只有现有目录与基线完全一致，才补登记 `20261104000100_arena_game`；不执行其建表或函数 SQL，不导入旧题。
- 定向修复包在同一事务中重新核对旧状态、安装三个课程函数、验证目标状态，再插入两条新账本。管理员历史只读。锁等待超过 5 秒或执行超过 30 秒会失败，不能留下部分修复。
- Arena 表短暂加 SHARE 锁，阻止检查期间并发改写；事务内前后行数必须一致。没有业务表的删除、更新、重建；失败时函数变更与两条账本一起回滚。
- 不部署连续练习、Arena 正式题库接入、自适应规则或前端，不执行整库 `db push`，不触碰其他工作区改动。

## 文件与执行

- `arena-baseline.json`：由未修改的旧 Arena 迁移在本地容器生成的目录基线，带源 SQL MD5。
- `course-read-policies.json`：本轮生产目录导出的五条课程读取策略；已人工核对其可见性调用。
- `00_preflight_readonly.sql`：五项检查均须为 true。查询仅涉及系统目录和迁移账本。
- `10_reconcile.sql`：一次性定向修复；Arena 源文仅用于登记，唯一动态执行项是课程 SQL。拒绝重复执行、未知函数/权限/结构和账本触发器。
- `20_verify_readonly.sql`：管理员原历史、两条新账本、课程函数及权限依赖、Arena 目录六项均须为 true。验收 SQL 不读取账号或题目内容。

本轮用户要求修复并 commit。仓库修复与生产执行分别报告；生产执行前提供可审阅 SQL 和本地验证结果，确认执行范围。先运行 preflight，若有 false 则停止调查，不修改预期值来强行通过。之后只执行一次 `10_reconcile.sql`，再运行只读验收。若响应超时，先查账本和只读验收，不盲目重试。

这里登记的 Arena `statements` 是已证明目录等价的仓库规范源文，不声称保留了当初 SQL Editor 的原始换行。已安装但内容不同的数据库不适用此包，需要另作前向修复。后续合法迁移修改相关函数后，应以新迁移验收为准，旧包不能重放。
