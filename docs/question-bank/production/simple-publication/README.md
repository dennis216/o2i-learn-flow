# 简化发布：仅新增迁移的上线材料

本目录为用户后续手动上线准备。本任务不执行生产 SQL、不 push、不部署网页。

生产五条旧题库迁移已由用户完成并回传账本匹配、168/168 目录检查通过；不重跑旧迁移、Task 4 上线包或 taxonomy。新增迁移是 `20261020000000_question_bank_simple_publication.sql`。

1. 确认 Supabase Dashboard 当前项目为 `lxoaeaewcrshjkigzyqe`。将 **10_deploy.sql 全文**复制到 SQL Editor，作为一次执行。它只运行这一个新迁移，核对五条旧迁移的原 SQL 指纹和被替换函数的旧定义，执行后核对 19 项目录条件，并在同一事务记录新迁移账本。任一步失败，DDL 与新增账本一起回滚；已记录的新迁移会拒绝重复运行。
2. 成功后独立运行 **20_verify_readonly.sql 全文**。只返回一个 `simple_publication_verification` 对象；`all_catalog_checks_pass`、`all_ledger_checks_pass` 都必须为 true。此查询只读元数据，不读取题目、答案或用户内容。
3. 数据库通过后再安排新版前端部署；旧页面仍发送旧审核 JSON，新接口会拒绝此格式，需同步更新并刷新页面。新页面在旧数据库上同样无法发布。不要以改字段、清 flags 或伪造审核值处理版本不匹配。
4. 使用真实管理员会话完成线上验收：旧草稿加载、Preview、选择/取消零写入；得到明确生产发布授权后，才验证实际 Publish 和刷新回读。8 道真实题无需重新导入；本地没有代做其真实内容审核或发布。

没有完整备份，本包不提供提交后的完整恢复能力。不要回滚到要求 source/calculator 非空的旧约束；新规则允许已发布版本保留 NULL，旧约束可能无法重新建立。需要恢复规则时应另做前向迁移并先评估已有数据。

审核记录和发布仍分两个阶段：最终 Publish 点击才开始写入；若后续发布失败，先保存的真实人工确认可能保留作为审计证据。发布本身仍是单个事务，题目状态、当前版本、版本转换和发布事件不会部分成功。
